# P0 级事故复盘报告：刷词机云同步“假成功”与学习数据不可恢复事件

**事故等级：P0 / 最高级别数据事故**  
**系统名称：考研词汇自动刷词机 / GitHub Pages + GitHub Gist 云同步方案**  
**核心后果：用户在 2026-06-18 约 1 小时学习记录未能从任何可用位置恢复；系统曾给出同步成功或无异常的用户感知，但 Gist 未保存对应数据。**

---

## 1. 事故摘要

本次事故不是单一页面显示 bug，而是一次完整的数据安全事故。事故链条包括：

1. 用户在网页端进行学习操作，预期学习记录被保存并同步到 GitHub Gist。
2. 页面右上角同步指示灯最终长期显示绿色或无异常，使用户形成“云端已保存成功”的判断。
3. 实际检查 GitHub Gist revision 后，未发现 2026-06-18 当日对应的学习数据版本。
4. 后续通过 `rescue.html` 分别检查手机与平板浏览器本地存储：
   - 手机端本地学习记录只到 2026-06-15。
   - 平板端 localStorage 只剩认证、设置、云同步配置和 syncMeta，不含 progress、activity、marks、pendingOps 等学习数据。
5. 因浏览器缓存 / 网站数据已被清理，且 Gist 历史没有 2026-06-18 数据，最终判断：2026-06-18 的约 1 小时学习记录大概率无法恢复。

本事故的本质是：

> 系统把“本地保存 / 同步尝试 / 没有立刻报错 / 读云端成功”等状态错误地包装成了“云端同步成功”，导致用户在没有真实云端落盘的情况下继续使用，最终在本地数据被清理后发生不可恢复丢失。

---

## 2. 影响范围

### 2.1 已确认影响

- 2026-06-18 用户约 1 小时学习记录大概率丢失。
- GitHub Gist 没有对应日期的 `sync.json` revision。
- 用户端曾经无明显错误提示，右上角同步状态灯最终显示绿色或无异常。
- 用户误以为云端已保存，后续清理缓存 / 网站数据后丢失本地唯一副本。

### 2.2 潜在影响

同类用户只要满足以下条件，也可能发生同类事故：

1. GitHub PAT 无效、过期、权限不足，或填写错误。
2. Gist ID 与 GitHub PAT 填写混淆。
3. 页面将“本地保存成功”或“无待同步任务”显示成绿色。
4. 用户未意识到云端未真正保存。
5. 用户清理浏览器网站数据、本地存储或更换设备。

---

## 3. 事故证据链

### 3.1 Gist 当前内容证据

用户提供的 Gist 当前 `sync.json` 包含：

- `activity.days` 中有：
  - `2026-06-10`
  - `2026-06-11`
  - `2026-06-15`
- 未发现：
  - `2026-06-18`
- `progress.27ky-shanguo-gaopin.lastWordId = 1462`
- `progress.27ky-shanguo-gaopin.unit = 20`
- `marks.known` 有少量历史标记

这说明 Gist 中存在历史学习数据，但不是 2026-06-18 的数据。

### 3.2 Gist revisions 证据

用户截图显示 Gist revisions：

- 最新 revision：约 6 小时前，类似恢复旧版本动作。
- 前一个明显 revision：约 4 天前。
- 再往前：last week。
- 未看到 2026-06-18 对应的 revision。

如果 2026-06-18 学习数据曾经成功 Push 到 Gist，理论上 Gist history 中应存在该日期附近的 revision。当前证据未显示该 revision。

### 3.3 手机 rescue 证据

手机 `rescue.html` 初步显示“发现 2026-06-18”，但后续检查完整 JSON 后确认这是误报。误报原因是救援工具扫描到了自身源码中的检测日期字符串，而非学习数据。

手机 localStorage 中真实学习数据仍只包含：

- `activity:27ky-shanguo-gaopin`：只有 `2026-06-10`、`2026-06-11`、`2026-06-15`
- `progress:27ky-shanguo-gaopin`：仍为 `lastWordId: 1462`、`unit: 20`
- `pendingOps`：空
- IndexedDB：空

### 3.4 平板 rescue 证据

用户上传的平板救援 JSON 显示：

- localStorage 总量约 996 bytes。
- localStorage 仅有 4 个 key：
  - `is_authenticated`
  - `vocab_machine_cloud_v1`
  - `vocab_machine_settings_v1`
  - `vocab_machine_sync_meta_v1`
- 不存在：
  - `activity:27ky-shanguo-gaopin`
  - `progress:27ky-shanguo-gaopin`
  - `marks:27ky-shanguo-gaopin`
  - `vocab_machine_pending_ops_v1`
- IndexedDB 为空。

这说明平板本地也没有可恢复的学习数据，只剩配置类数据。

### 3.5 云同步配置异常证据

手机和平板导出的本地配置都显示过异常现象：

```json
{
  "token": "4d81...",
  "gistId": "4d81..."
}
```

即 GitHub PAT 和 Gist ID 被保存成了同一个值。这在正常情况下几乎不应出现。其含义是：

- 用户可能把 Gist ID 粘贴到了 PAT 输入框；或
- 页面没有做字段格式校验；或
- 配置保存/恢复逻辑存在混淆；或
- UI 将两个字段都隐藏成密码框，导致用户无法肉眼核对。

无论哪种情况，系统都不应继续进入“云同步成功”状态。

## 4. 事故经过重建

### 阶段一：早期已有云端数据

Gist 中已有 2026-06-10、2026-06-11、2026-06-15 等历史数据。说明云端同步曾经在某个阶段成功或用户曾经手动恢复过旧数据。

### 阶段二：2026-06-18 用户进行学习

用户在平板端刷词约 1 小时，预期产生大量：

- activity day 记录；
- wordIds；
- 学习时长 seconds；
- progress；
- marks 或 pendingOps。

### 阶段三：云同步没有真实落盘

Gist revisions 没有 2026-06-18 对应版本。结合本地配置中 token 与 gistId 相同，可推断当时云同步 Push 大概率没有成功。

### 阶段四：页面没有有效提示

用户反馈右上角同步灯：

- 未显示明确报错；
- 最后一直是绿色；
- 用户据此认为同步成功。

此处是事故最关键的“用户误导点”。

### 阶段五：本地数据被清理或覆盖

后续浏览器缓存/网站数据被清理，或者页面被旧云端快照覆盖。本地唯一副本消失。

### 阶段六：恢复旧 Gist 版本

今日曾恢复 Gist 旧版本，但恢复的是四天前/更早数据，而不是 2026-06-18 数据。

### 阶段七：救援检查确认不可恢复

手机和平板 rescue JSON 均未发现真实的 2026-06-18 学习数据。Gist history 也未发现对应 revision。因此判定数据大概率不可恢复。

## 5. 根因分析

### 根因一：同步状态灯语义严重错误

现有状态灯只有大致的 `idle / syncing / ok / error`，且 `ok` / `error` 会在短时间后隐藏或回到 idle。更严重的是，代码中存在多种路径会调用 `setSyncStatus("ok")`，但这些路径并不都代表“云端 PATCH 成功”。

正确语义应为：

> 绿色只能表示 GitHub Gist PATCH 成功返回 2xx，并且本地记录了新的 remote revision。

错误语义包括：

- 本地保存成功就显示绿色；
- 拉取云端成功就显示绿色；
- 没有发现本地变化就显示绿色；
- 同步流程没有运行但保持绿色；
- 错误两秒后消失，用户看不到失败。

本事故中，用户正是被绿色或无异常状态误导。

### 根因二：PAT 和 Gist ID 没有格式校验

系统允许 `token === gistId` 的配置继续保存，并进入同步流程。这是严重错误。

GitHub PAT 与 Gist ID 在格式上不同：

- classic PAT 通常以 `ghp_` 等前缀开头；
- fine-grained token 通常以 `github_pat_` 开头；
- Gist ID 是十六进制样式字符串；
- 两者不应相等。

系统应在输入阶段直接阻断，而不是等 GitHub API 返回 401 后再模糊报错。

### 根因三：没有“云端最后成功保存”的硬指标

系统没有在 UI 中明确展示：

- 最后一次 GitHub PATCH 成功时间；
- 最后一次成功 revision；
- 当前 pendingOps 数量；
- 当前本地是否有未上传数据；
- 最近一次同步错误。

用户无法判断数据是否真正云端落盘。

### 根因四：错误状态不持久

代码中的 `setSyncStatus("error")` 会在短时间后回到 idle。对数据系统而言，这是错误设计。同步失败不是动画状态，而是数据风险状态。

正确设计应为：

- 同步失败红色常驻；
- 本地有未上传数据橙色常驻；
- 只有成功 Push 后才绿色；
- 错误必须出现在设置页和主界面，而不只是右上角小点。

### 根因五：过度依赖 pagehide / visibilitychange / keepalive

当前代码中在 `visibilitychange` 和 `pagehide` 时调用 `autoPushToGist({ keepalive: true })`。这类浏览器生命周期事件不可靠，尤其在移动浏览器、PWA、后台切换、省电模式下，网络请求可能被取消、截断或不返回结果。

这种机制只能作为辅助，不应作为主同步保障。

### 根因六：缺少本地耐久备份

学习数据只保存在普通 localStorage key 中，没有：

- 每日备份；
- 滚动快照；
- 写前日志；
- 导出提醒；
- 本地灾难恢复入口。

当 localStorage 被清理或被旧云端覆盖后，没有本地第二副本。

### 根因七：没有上传审计日志

系统无法回答这些关键问题：

- 某次学习操作是否写入本地；
- 是否进入 pendingOps；
- 是否尝试 Push；
- Push 返回状态码是什么；
- 成功后 revision 是什么；
- 失败时错误是什么。

这导致事故后只能靠截图、Gist history、localStorage 残留逆向推断。

### 根因八：Service Worker 和缓存使部署验证复杂化

多次出现：

- 上传新代码后设备仍跑旧 app.js；
- rescue.html 访问失败；
- 首页路径被旧缓存拦截；
- index.html / app.js 版本参数与 sw 缓存不一致。

这增加了救援难度，也影响用户对修复结果的判断。

---

## 6. 为什么这是 P0 而不是普通 bug

普通 bug 通常只影响显示或一次操作。本事故具有以下特征：

1. **数据不可逆损失**：学习记录无法从 Gist、本地、IndexedDB 恢复。
2. **用户被错误状态误导**：绿色灯暗示同步成功。
3. **事故静默发生**：没有及时红色常驻错误。
4. **恢复能力不足**：无每日本地备份，无可靠审计日志。
5. **架构层问题**：不是单个按钮问题，而是同步协议、状态机、UI 语义、备份策略同时失败。
6. **可能复现于其他用户**：任何 PAT 错误或 Gist 配置错误用户都可能遭遇。

因此应按 P0 处理，优先级高于任何功能开发。

---

## 7. 数据恢复结论

当前已检查路径：

1. 当前 Gist `sync.json`：无 2026-06-18。
2. Gist revisions 截图：无明显 2026-06-18 revision。
3. 手机 localStorage：无真实 2026-06-18 学习数据。
4. 平板 localStorage：无学习数据，仅配置。
5. IndexedDB：空。
6. pendingOps：不存在或为空。

因此结论为：

> 若没有其他尚未检查的设备或浏览器保留网站数据，2026-06-18 的约 1 小时学习数据大概率不可恢复。

唯一仍可能存在数据的位置：

- 昨天实际使用过但尚未清理网站数据的其他浏览器；
- 系统级浏览器备份；
- 设备级完整备份；
- 未同步但仍打开着旧页面的标签页内存。

如果这些都不存在，则无法恢复。

## 8. 必须立即停止的行为

在完成 P0 修复前：

1. 不要继续宣传云同步可靠。
2. 不要让绿色灯表示模糊成功。
3. 不要依赖页面关闭时上传。
4. 不要在 PAT 无效时允许继续显示绿色。
5. 不要允许 `token === gistId`。
6. 不要在本地有未上传数据时自动拉旧云端覆盖本地。
7. 不要清空 pendingOps，除非云端 PATCH 成功。
8. 不要把同步失败两秒后隐藏。

---

## 9. 必须立即修复的原则

### 9.1 状态灯语义重新定义

- 绿色：云端已确认保存。必须满足：最近一次本地修改已成功 PATCH 到 Gist，并记录新 revision。
- 蓝色/黄色：同步中或有待上传数据。
- 橙色：本地有未上传数据，云端未确认。
- 红色：同步失败，云端未保存。
- 灰色：未配置云同步，不能称为已同步。

### 9.2 错误必须常驻

只要最近一次 Push 失败，错误必须常驻到用户修复配置并成功上传为止。

### 9.3 本地必须有灾难备份

每次关键学习操作后，至少写入：

- 主业务 key；
- pendingOps；
- daily backup；
- latest local snapshot。

### 9.4 GitHub PAT 必须严格校验

保存云同步配置前检查：

- token 非空；
- gistId 非空；
- token 与 gistId 不相等；
- token 形态不像 gistId；
- gistId 形态不像 token；
- GitHub API 能成功 GET；
- 测试 PATCH 不应破坏业务数据，可写 `sync.healthcheck.json`。

### 9.5 云同步成功必须以 GitHub 返回为准

只有当：

1. PATCH 返回 2xx；
2. response JSON 中有新的 `history[0].version` 或 `updated_at`；
3. 本地 `lastRemoteVersion` 已更新；
4. pendingOps 已清空；

才允许显示绿色。

## 10. 后续行动优先级

### P0：立即修复

1. 状态灯语义重构。
2. PAT/Gist ID 校验。
3. Push 失败常驻红色错误。
4. 有 pendingOps 时常驻橙色。
5. 每日本地备份。
6. 最近一次成功云端保存时间展示。
7. 设置页展示 pendingOps 数量、lastRemoteVersion、lastSuccessfulPushAt。
8. 禁止 token 与 gistId 相同。

### P1：恢复能力建设

1. Gist history 恢复工具。
2. localStorage 备份导入工具。
3. 自动合并本地备份与云端数据。
4. 导出/导入完整 sync.json。

### P2：架构优化

1. 将 Gist 同步抽象成可测试模块。
2. 引入单元测试与模拟 GitHub API。
3. 将 Service Worker 与主同步隔离。
4. 更完善的 operation log / snapshot 策略。

---

## 11. 事故定性

本事故不是用户误操作单独造成的。即使用户填错 PAT 或清理缓存，系统也应做到：

- 明确阻止错误配置；
- 明确提示云端未保存；
- 保留本地备份；
- 禁止假成功；
- 提供恢复路径。

本系统没有做到这些，因此应定性为：

> 同步状态设计缺陷 + 配置校验缺失 + 云端落盘确认缺失 + 本地灾备缺失共同导致的 P0 数据事故。
