## 2. 刷词交互契约，禁止改反

这些方向是用户已经确认过的正确逻辑：

- 卡片左侧热区：上一个词。
- 卡片右侧热区：下一个词。
- 卡片中间：暂停/继续播放。暂停后再点中间继续播放，并有轻量反馈。
- 右滑：上一个词，也就是向前。
- 左滑：下一个词，也就是向后。
- 上滑：标记为已斩/认识，并进入下一个词。
- 下滑：只标记为重难点/生词，不进入下一个词，不暂停，当前词继续正常播放时序。
- 撤销按钮必须区分 `撤销上滑` 和 `撤销下滑`。
- 已经标记过的词，无论手动回退还是自动播放再次走到该词，都要显示对应撤销按钮。
- 右侧提示栏按钮含义：`↑` 已斩并进入下一个，`↓` 标记重难点但不跳词，`←` 上一个，`→` 下一个。
- 卡片滑动契约和右侧提示栏箭头契约不要混淆：卡片左滑仍是下一个，右滑仍是上一个。
- 连续快速点击上一词/下一词必须按点击次数执行，动画期间点击进入导航队列，不要丢点击。

## 3. 播放时序契约

播放倍速现在语义是 `朗读倍速`，只控制 Web Speech 的英文/中文朗读速度，不控制停留和延迟。

每张卡片的时序：

1. T0 立即显示英文卡面，中文必须隐藏，不能闪现一瞬间。
2. `中文出现延迟` 从 T0 开始计时，是绝对毫秒值。
3. 先执行 `读前停留`，是绝对毫秒值。
4. 英文朗读或英文估算阅读阶段。
5. 中文朗读必须在英文阶段结束并且中文已经显示之后执行；中文朗读关闭时仍给中文估算阅读时间。
6. 中文阶段结束后执行 `读后停留`，是绝对毫秒值。
7. 自动模式下进入下一词；手动模式下停在当前词，等用户手势/点击切换。

注意：`读前停留`、`中文出现延迟`、`读后停留` 不允许随朗读倍速缩放。

## 4. 重难点词库模式

- 重难点来源是当前词书 `marks.unknown`。
- 可以刷当前 Unit 的重难点，也可以刷整本词书重难点。
- 重难点模式复用主刷词界面的朗读设置、停留设置、手势逻辑、手动模式和统计。

- 进度键规则：
  - 主词库：`progress:<bookId>`
  - Unit 重难点：`unknown_progress:<bookId>:unit:<unit>`
  - 整本重难点：`unknown_progress:<bookId>:book`

## 6. P0 Gist 同步安全模型

当前同步模型已经重构为：`单心跳 syncTick + 稳定业务 hash + Gist PATCH 后 GET 校验 + 自动 safe merge`。

这次重构的背景是 P0 数据事故：同步失败时不能假装成功，更不能显示绿灯。后续维护必须遵守一个最高优先级原则：

> 右上角绿色 `云端已保存` 只能表示本轮业务 `sync.json` 已经 GitHub PATCH 成功，并且 PATCH 后立即 GET 到的云端 `sync.json` 业务 hash 与本轮上传 payload hash 完全一致。除此之外，任何状态都不能显示绿色。

### 6.1 当前代码入口

关键实现位置在 `app.js`：

- `businessPayloadForHash()` / `businessPayloadHash()`：稳定业务 hash。
- `markLocalDirtyAfterBusinessWrite()`：本地学习数据变化后的统一 dirty 标记入口。
- `initializeP0Sync()`：新版本启动/配置保存后的初始化同步逻辑。
- `syncTick()`：唯一主同步心跳入口。
- `patchBusinessPayloadToGist()`：PATCH `sync.json` 并立刻 GET 校验云端 hash。
- `finalizeVerifiedPatch()`：PATCH 校验成功后，根据当前本地 hash 决定是否清 dirty 和显示绿色。
- `safeMergePayloads()`：双端变化时自动合并。
- `applySyncPayload()`：应用云端 payload，带 `applyingRemotePayload/suppressDirty` 保护。
- `renderSyncDiagnostics()`：设置页同步诊断面板。

旧的 `pendingOps` / v2 ops 相关函数仍可能保留用于兼容和诊断，但 P0 主状态机不再依赖 `pendingOps` 判断是否能同步成功。不要把旧 `runGistSync()` / revision-only 逻辑改回主路径。

### 6.2 稳定业务 hash

所有同步判断统一使用 `businessPayloadHash()`。该 hash 必须先 normalize，再只抽取固定业务字段：

- `progress`
- `unknownProgress`
- `marks`
- `activity`
- `unitStats`

明确不允许进入业务 hash 的内容：

- GitHub PAT / `token`
- `gistId`
- `syncMeta`
- hash 同步状态
- backup / audit / pendingOps
- UI 临时状态
- `updatedAt` 等非业务时间戳
- `settings`（本机 UI/播放设置，不参与业务 hash，避免设置变化触发学习数据反复 dirty）

维护要求：只要新增会影响学习结果的字段，就必须评估是否要加入业务 hash；不要把凭据、诊断、备份、审计数据加入 hash。

### 6.3 本地同步状态键

新增本地状态键：`vocab_machine_hash_sync_state_v2`（兼容读取旧 v1）。

核心字段：

- `localDirty`：本地是否明确有未上传修改。
- `baseRemoteHash`：本地认为的云端基线业务 hash。
- `localPayloadHash`：最近一次记录的当前本地业务 hash。
- `dirtySince`：本地进入 dirty 的时间。
- `lastSyncStatus`：最近同步状态。
- `lastSyncError`：最近同步错误。
- `lastSuccessfulPushAt`：最近一次真正云端保存成功时间。
- `lastSuccessfulPullAt`：最近一次从云端加载成功时间。
- `consecutiveSyncFailures`：连续失败次数，用于退避。
- `nextRetryAt`：下一次允许自动重试时间。
- `lastBackupError`：备份/本地状态写入异常。

有效脏状态必须动态计算：

```txt
effectiveDirty = localDirty === true || localPayloadHash !== baseRemoteHash
```

后续任何同步分支都不能只相信 `localDirty`。这是为了防止旧版本、异常或 localStorage 写入不完整导致 dirty 标记丢失。

仍保留的旧键：

- `vocab_machine_sync_meta_v1`：兼容旧诊断、clientId、旧同步元信息。
- `vocab_machine_pending_ops_v1`：旧 pendingOps 队列，仍可用于诊断和兼容，但不是 P0 主状态机决策依据。
- `vocab_machine_local_snapshot_latest_v1`：旧最新本地快照，继续写入，便于救援。
- `vocab_machine_daily_backup_YYYY-MM-DD`：旧每日备份，继续写入。
- `vocab_machine_sync_audit_v1`：旧审计事件。

### 6.4 配置硬拦截

以下配置一律视为不可信，必须禁止 Pull、禁止 Push、禁止显示绿色：

- token 为空。
- gistId 为空。
- `token === gistId`。
- token 看起来像 Gist ID，例如纯十六进制长串。
- gistId 看起来像 PAT，例如 `ghp_` / `github_pat_` / `gho_` / `ghu_` / `ghs_` / `ghr_` 开头。

设置页输入框只写 `cloudConfigDraft`，不能边输入边保存、边输入边同步。

只有点击“测试并保存云同步配置”且通过以下步骤后，才允许保存配置：

1. 本地格式校验通过。
2. GET Gist 成功。
3. PATCH `_sync_probe.txt` 成功，确认可写。

注意：`_sync_probe.txt` 只证明当前 PAT 对该 Gist 可写。它会改变 Gist 全局 revision，但不代表业务 `sync.json` 保存成功，不能更新 `baseRemoteHash`，不能写 `lastSuccessfulPushAt`，不能显示绿色。

### 6.5 启动初始化逻辑

新版本启动后先写 `startup` 保护快照，再校验配置。配置不可信时只显示配置错误，不 Pull、不 Push。

配置可信时，初始化逻辑是：

1. GET 云端 `sync.json`。
2. 计算 `currentRemoteHash`。
3. 收集本地业务 payload。
4. 判断本地是否严格空。
5. 计算 `localPayloadHash`。
6. 计算 `effectiveDirty`。

分支规则：

- 本地严格空，云端有 `sync.json`：自动 Pull 云端，更新 `baseRemoteHash/localPayloadHash`，`localDirty=false`，状态为 `cloud_loaded`，不是绿色。
- 本地严格空，云端没有 `sync.json`：空白启动，不上传空快照，不显示绿色。
- 本地不空且 `effectiveDirty=false`，云端 hash 与 `baseRemoteHash` 不同：自动 Pull 云端，但 Pull 前仍要保护本地。
- 本地不空且 `effectiveDirty=true`：禁止强拉云端覆盖本地，直接进入页面，交由后台 `syncTick()` 上传或 safe merge。

严格空本地不仅要检查当前业务数据，也要检查本地 P0 backup。只要 backup 中存在非空学习数据，不得视为严格空。

严格空判断包含：

- `marks.known/unknown` 全空。
- 主进度没有有效 `lastWordId`。
- 重难点进度没有有效 `lastWordId`。
- `activity.days` 没有有效 `words/known/unknown/wordIds/seconds`。
- `unitStats` 没有完成记录。
- P0 backup 中没有非空学习 payload。

禁止用 `syncContentScore < 20` 判断本地为空。分数阈值只能用于危险上传熔断或人工诊断，不能用于“能不能自动 Pull 覆盖本地”。

### 6.6 用户操作后的本地保护

所有会改变学习数据的入口都要在业务 localStorage 写入后调用本地 dirty 逻辑。当前统一入口是 `onLocalDataChanged()` -> `markLocalDirtyAfterBusinessWrite()`。

每次背词、标记、撤销、推进进度、修改设置、记录 activity、记录 unitStats 后必须做到：

1. 先写业务 localStorage。
2. 重新收集业务 payload。
3. 重新计算并保存 `localPayloadHash`。
4. 设置 `localDirty=true`。
5. 如果还没有 `dirtySince`，写入当前时间。
6. 写旧 `vocab_machine_local_snapshot_latest_v1`。
7. 写旧每日备份 `vocab_machine_daily_backup_YYYY-MM-DD`。
8. 写 P0 `latest` backup。
9. 写 P0 daily backup。
10. 更新右上角状态。
11. 触发一次 `syncTick({ reason: "local_change", bypassBackoff: true })`。

注意：应用云端 payload 时必须通过 `applyingRemotePayload/suppressDirty` 保护，不能触发 dirty 标记，也不能生成新的 pendingOps。

### 6.7 单心跳机制

当前只允许一个主同步心跳：

```js
setInterval(() => syncTick({ reason: "heartbeat" }), 5000)
```

`pagehide`、`visibilitychange`、返回设置页、阶段总结等可以触发兼容同步入口，但入口最终都必须进入 `syncTick()`，不能另起第二套 GET/PATCH 流程。

`syncTick()` 前置拦截：

- `state.isSyncing === true`：直接返回，禁止并发同步。
- `document.hidden === true`：直接返回，不把隐藏页 keepalive 当主同步机制。
- heartbeat 场景下如果界面空闲且 `effectiveDirty=false`：直接返回。
- 如果还在失败退避时间内，且不是用户新操作或回前台触发：直接返回。

注意：如果 `effectiveDirty=true`，即使当前看起来 idle，也必须继续尝试同步。

所有同步流程必须用 `try/finally` 恢复 `state.isSyncing=false`。网络失败、PATCH 失败、GET 校验失败都不能把 `localDirty` 清掉。

连续失败退避：5s、15s、30s、60s、120s，之后最多 5 分钟。用户新操作或回前台会 `bypassBackoff=true` 立即尝试一次。

### 6.8 空云端保护后的同步状态机

每次 `syncTick()` 都会 GET 云端 `sync.json`，重新计算：

- `currentRemoteHash`
- 当前本地 `localPayloadHash`
- `effectiveDirty`
- `localHasBusinessData`
- `remoteHasBusinessPayload`
- `remoteIsEmptyPayload`

远端解析规则：

- `missing` / `empty` / `valid_empty`：远端为空。
- `valid_nonempty`：远端有业务学习数据。
- `invalid` / `v2_unknown_ops`：停止自动同步并弹诊断；绝不能当作空云端。
- 解析不到 payload 时不能默认当空，必须停止并诊断。

#### A. 本地非空 + 云端空

动作：

1. 禁止直接 Pull 云端空 payload。
2. 弹窗诊断 `REMOTE_EMPTY_LOCAL_HAS_DATA` 或 `READONLY_REMOTE_EMPTY_LOCAL_HAS_DATA`。
3. 可写时保持本地 dirty，并尝试 Push 本地非空 payload。
4. 只读时保持 `localDirty=true`，状态为 `dirty_read_only/read_only`，提示更换可写 PAT。
5. 不能显示 `cloud_saved` / `cloud_loaded`，不能清 dirty。

#### B. 本地空 + 云端空

动作：

1. 状态保持 `local_only`。
2. 不 Pull、不 Push、不创建空 `sync.json`。
3. `localDirty=false`，`localRecoveryRequired=false`。
4. 不写 `lastSuccessfulPushAt` / `lastSuccessfulPullAt`，不显示成功态。

#### C. 本地空 + 云端非空

动作：

1. 允许直接 Pull。
2. Pull 前再次检测同步期间是否产生本地变化。
3. 如果本地变脏，取消直接 Pull，改走 safe merge。
4. Pull 后必须读回本地 hash，只有 `localAfterApplyHash === remoteHash` 才能 `cloud_loaded`。
5. Pull 成功也不能显示绿色 `cloud_saved`。

#### D. 本地非空 + 云端非空 + hash 不同

动作：

1. 禁止强拉云端覆盖本地。
2. 可写时写 `pre_merge` backup，safe merge 后 PATCH，PATCH 后 GET hash 校验成功才可能 `cloud_saved`。
3. 只读时只允许在本地应用 safe merge 结果，保持 `localDirty=true` 和 read-only，等待更换可写 PAT 后上传。
4. 只读本地合并不能改 `baseRemoteHash` 为 merged hash，不能写 `lastSuccessfulPushAt`，不能 `cloud_saved` / `cloud_loaded`。
5. 如果同步期间用户又操作，保持 dirty，不显示绿色，下一轮继续上传。
### 6.9 Safe Merge 规则

safe merge 不弹窗，不让用户手动选择保留哪端。程序自动合并，但不能让云端霸权覆盖本地未上传数据。

规则：

- `progress`：取更靠后的进度，依据 `unit * 100000 + lastWordId`。
- `unknownProgress`：book 进度和各 Unit 进度分别取更靠后的进度。
- `activity`：按日期合并；`wordIds` 并集；`seconds/words/known/unknown` 取较大值，避免重复累计。
- `marks.known/unknown`：同一 wordId 必须互斥；双端冲突时当前设备本地优先。
- `unitStats`：同 Unit 取较大的 `completed`。
- `settings`：当前设备本地优先。
- 任一端独有的学习记录必须保留，不得删除。

### 6.10 右上角同步状态语义

状态集合：

- `unconfigured`：未配置云同步。
- `invalid_config`：配置不可信或格式明显错误。
- `local_only`：只确认本地保存，未确认云端保存。
- `dirty`：本地有未上传数据。
- `syncing`：正在同步。
- `cloud_loaded`：已从云端加载或更新；不是绿色。
- `cloud_saved`：唯一绿色状态，必须来自本轮 PATCH + GET hash 校验成功。
- `read_only`：可读但不可写，或 PAT 无效/无写权限。
- `error`：同步失败，本地 dirty 保留。
- `conflict`：自动合并失败，本地 dirty 保留。

禁止事项：

- 分支 A 无变化不能显示绿色。
- 初始化 Pull 成功不能显示绿色。
- healthcheck 成功不能显示绿色。
- 只 GET 成功不能显示绿色。
- PATCH 成功但未 GET 校验不能显示绿色。
- PATCH 成功且 GET 校验成功，但同步期间用户又产生新本地操作，也不能显示绿色。

### 6.11 Gist 文件协议

Gist 文件：

- `sync.json`：正式业务快照，仍是完整 `version: 1` payload。
- `sync.prev.json`：每次业务 Push 前的旧云端内容备份。
- `sync.backup.YYYY-MM-DD.json`：当天云端业务备份。
- `_sync_probe.txt`：配置页写权限测试文件，只用于验证可写，不参与业务 hash。

读取 Gist 时要注意：

- `file.truncated === true` 或没有 `file.content` 时，必须通过 `raw_url` 读取完整内容。
- 如果 token 无效但 Gist 公开，代码可能能 GET 到云端，但必须进入 `read_only`，不能上传或显示绿色。

### 6.12 本地备份规则

P0 备份 key：

```txt
vocab_machine_backup:startup:<timestamp>
vocab_machine_backup:pre_pull:<timestamp>
vocab_machine_backup:pre_push:<timestamp>
vocab_machine_backup:pre_merge:<timestamp>
vocab_machine_backup:latest
vocab_machine_backup:daily:<YYYY-MM-DD>:latest
vocab_machine_backup:daily:<YYYY-MM-DD>:first_non_empty
vocab_machine_backup_index_v1
```

维护要求：

- `startup` 在新版本启动时写入，用于迁移前保护。
- `pre_pull` 在远端覆盖本地前写入。
- `pre_push` 在本地上传前写入。
- `pre_merge` 在自动合并前写入。
- `latest` 在每次本地业务操作后更新。
- `daily:first_non_empty` 当天只写第一个非空学习 payload。
- 关键备份索引保留最近 20 条，并尽量保留最新 `startup`。
- localStorage quota/security 错误必须 catch，不能打断用户学习数据保存。
- 备份和诊断默认不能导出完整 GitHub PAT。

### 6.13 UI 行为限制

正常背词过程中，同步不得打断用户：

- heartbeat 不弹窗、不 toast、不拉横幅。
- 自动上传不弹窗、不 toast、不拉横幅。
- 自动合并不弹窗、不 toast、不拉横幅。
- 自动重试不弹窗、不 toast、不拉横幅。
- 分支 A 无变化不弹窗、不 toast、不拉横幅。

正常同步只更新右上角状态文字和颜色。

允许明显提示的场景：

- 页面初始化 Loading，例如“正在同步云端数据...”。
- 初始化 Pull 完成后的短提示，例如“已从云端加载”。
- 进入页面时发现本地有未上传数据，可短提示“本地进度已保留，正在后台保存”。
- 用户主动进入设置页、诊断页、测试云同步配置时显示详细结果。

### 6.14 Service Worker / 缓存

- `sw.js` 当前不缓存资源，`fetch` 直接 return。

## 7. 数据救援建议

如果用户清缓存后发现云端数据异常或丢失：

1. 先不要继续在当前页面刷词，避免产生更多本地改动并上传。
2. 到 GitHub Gist 历史里恢复 `sync.json` 上一个有数据的版本。
3. 检查 `sync.prev.json` 和 `sync.backup.YYYY-MM-DD.json` 是否有可用备份。
4. 如果浏览器本地还没清空，导出设置页“本地完整备份 JSON”。
5. 检查 localStorage 中的 P0 备份：
   - `vocab_machine_backup:latest`
   - `vocab_machine_backup:startup:<timestamp>`
   - `vocab_machine_backup:pre_pull:<timestamp>`
   - `vocab_machine_backup:pre_push:<timestamp>`
   - `vocab_machine_backup:pre_merge:<timestamp>`
   - `vocab_machine_backup:daily:<YYYY-MM-DD>:first_non_empty`
6. 使用 `rescue.html` 时，只能扫描业务 localStorage 和备份 key，不要把工具自身源码或缓存里的 `app.js` 当成用户数据。
7. 修复云端后，严格空本地可以自动 Pull；如果本地仍有学习痕迹，不能强拉覆盖，应该走后台 syncTick 上传或 safe merge。

## 8. 高风险维护点

- 不要把下滑改成自动下一词。下滑只标记重难点，不暂停、不跳词。
- 不要把左右滑动和左右点击改反：右滑/左热区是上一个；左滑/右热区是下一个。
- 不要把右侧提示栏改反：`←` 上一个，`→` 下一个；这与卡片滑动方向契约不是同一件事。
- 不要让中文释义在新卡 T0 闪现。
- 不要把 `读前停留`、`中文出现延迟`、`读后停留` 绑定到朗读倍速。
- 不要让 `播放倍速/朗读倍速` 控制非朗读延迟。
- 不要用本地空快照覆盖云端。
- 不要用 `syncContentScore < 20` 判断本地为空。
- 不要在本地 dirty 时强拉云端覆盖。
- 不要在 Pull 或 applyRemotePayload 时触发 dirty 或生成 pendingOps。
- 不要绕过配置硬拦截；token 和 gistId 明显填错时不能 Pull、不能 Push、不能绿灯。
- 不要把 healthcheck 成功当作业务保存成功。
- 不要在 PATCH 之后跳过 GET hash 校验。
- 不要在同步期间用户又操作后清 `localDirty`。
- 不要让分支 A、初始化 Pull、只 GET 成功显示绿色。
- 不要在正常背词时弹窗、toast、横幅打断用户同步状态。
- 不要在 P0 阶段重新缓存 `app.js`。
- 不要在导出备份或诊断时包含完整 GitHub PAT。

## 9. 必测清单

基础静态检查：

- `node --check app.js`
- `node --check sw.js`
- `git diff --check`

同步必测：

- 版本一致性：页面角标、诊断摘要、`version.json`、`app.js` loader、`00-env.js`、`sw.js` 都必须是 `2026-06-21-p14-sync-architecture-cleanup`。
- 本地非空 + 云端 `valid_empty` + 可写 PAT：不 Pull，保留本地，弹 `REMOTE_EMPTY_LOCAL_HAS_DATA`，随后尝试 Push；只有 PATCH+GET hash 成功才 `cloud_saved`。
- 本地非空 + 云端 `valid_empty` + 只读 PAT：不 Pull，保留本地，状态 dirty/read-only，弹 `READONLY_REMOTE_EMPTY_LOCAL_HAS_DATA`，不清 dirty。
- 本地空 + 云端 `valid_empty`：`local_only`，不 Push、不 Pull、不 `cloud_saved`、不 `cloud_loaded`。
- 本地空 + 云端 `valid_nonempty`：允许 Pull；本地 hash 校验成功才 `cloud_loaded`。
- 本地非空 + 云端 `valid_nonempty` + base hash 不同：进入 safe merge，不强拉覆盖。
- 云端 `invalid` / `v2_unknown_ops`：不当作空云端，不自动覆盖，弹窗提示云端无法安全解析。
- 同步 GET/Pull 期间继续刷词：Pull 前检测本地变化，取消直接 Pull，改走 safe merge。
- 同步问题弹窗复制内容必须包含 `remote.kind`、`remoteHash`、`localHasBusinessData`、`remoteHasBusinessData`、`baseRemoteHash`、`localPayloadHash`、`localDirty`、`effectiveDirty`、`readOnly`、`runId`、`APP_VERSION`、`APP_BUILD_ID`。- 空 token、空 gistId、`token===gistId`、token 像 Gist ID、gistId 像 PAT：全部不 Pull、不 Push、不绿灯。
- “测试并保存云同步配置”成功后，只显示配置可写，不能显示 `云端已保存`。
- healthcheck PATCH 改变 Gist revision 后，不能把 healthcheck revision 当作业务 `sync.json` 变化。
- 清缓存/新设备 + 云端有 `sync.json`：严格空本地自动 Pull，不能 Push 空数据，成功状态是 `已从云端更新`，不是绿色。
- 本地有 1 个标记、1 个进度、1 条 activity 或任一非空 backup + 首次绑定已有云端：不得当作严格空本地。
- 本地 dirty + 云端有数据：禁止强拉云端覆盖本地。
- 云端无 `sync.json` + 本地有数据：后台创建云端业务快照；PATCH 后 GET hash 校验成功才绿灯。
- 分支 A：云端 hash 等于 `baseRemoteHash` 且本地不脏，不写云端，不显示绿色。
- 分支 B：云端没变、本地脏，PATCH + GET hash 成功后，当前本地 hash 未变才清 dirty 和绿灯。
- 分支 B：PATCH/GET 期间用户继续操作，必须保持 dirty，不显示绿色，下一轮继续上传。
- 分支 C：Pull 前二次确认 dirty；如果同步期间本地变脏，取消 Pull 并改走 safe merge。
- 分支 C：Pull 成功只显示 `已从云端更新`，不显示绿色。
- 分支 D：双端变化时自动 safe merge；merge 后 PATCH + GET hash 校验成功且当前本地 hash 未变才绿灯。
- PATCH 失败、GET 校验失败、hash 不匹配：保持 dirty，进入退避重试，不显示绿色。
- 连续失败退避生效；用户新操作或回前台能跳过退避立即重试一次。
- `applySyncPayload()` 应用云端数据时不触发 dirty，不生成 pendingOps。
- 设置页诊断不显示完整 PAT。
- 导出本地备份不包含完整 PAT。
- `sync.prev.json` 写的是 Push 前旧云端内容。
- P0 本地备份能写入 `latest/startup/pre_pull/pre_push/pre_merge/daily:first_non_empty`。
- localStorage quota 异常不会打断用户学习数据保存。
- Service Worker 不缓存新版 `app.js`，刷新后能拿到 `2026-06-21-p14-sync-architecture-cleanup`。
